# 指示文：潮見と凪を「エージェントと言える」形にする（1〜4）

このファイルは、個人ポートフォリオのセッションで作った、Umi の開発セッションあての指示文です。

## 目的

ポートフォリオの「Read the story」に Umi の開発秘話を書きます。背景は、本人の言葉では次の2つです。
- タスク管理アプリがほしかった
- 授業で習った技術（ADK、A2A、エージェント同士の連携）を、実際に使ってみたかった

ところが今の潮見は「Gemini を1回呼んで点数を返すだけ」で、エージェントとは言いにくい状態です。凪も、道具は受け取ったデータを読み直すだけです。A2A も、決まった順番で呼ぶだけなので、関数呼び出しと変わりません。
そこで次の 1〜4 を行い、「ADK と A2A を使ったエージェント連携」と言い切れる形にします。

## 今のつくり（2026-11-28 時点、最新 682d7bb）

- `server/agents.js`：A2A の共通部（エージェントカード、JSON-RPC `message/send`、Firebase トークンの確認、Gemini 呼び出し）
- `functions/api/agents/shiomi.js`：潮見。Gemini を1回呼び、構造化 JSON で点数を返す。道具も記憶もない
- `functions/api/agents/nagi.js`：凪。関数呼び出しの道具は4つ。ただし get_free_time は「未接続」を返すだけで、残りは渡されたレポートの読み直し
- `functions/api/nagi.js`：外側のコードが「潮見 → 凪」の順に A2A で呼ぶ（順番はコードが決めている）
- ADK 版は `docs/reference/adk-agents/` に参考として保管しているだけで、本番では使っていない
- 設計書は `docs/nagi-agent-design.md`

## やること

### 1. 潮見に記憶を持たせる（保存先は Cloudflare D1）

D1 は Cloudflare の SQLite で、表（テーブル）としてデータを持てます。Cloudflare のダッシュボードで表として中身を見ることもできます。

記録するもの（表の案。列は必要に応じて調整してよい）：
- `corrections`：潮見の値をユーザーが手で直したとき。uid、task_id、タイトル、項目（impact / penalty / effort / dependency / must）、潮見の値、ユーザーの値、日時
- `actuals`：ダイブが終わったとき。uid、task_id、タイトル、潮見の effort、見積もり分、実際にかかった分、日時
- `clarifications`：2 で潮見が聞き返し、ユーザーが答えたとき。uid、task_id、質問、答え、日時

使い方：
- 記録はアプリ側から行う。値の手直しとダイブ終了のときに、Pages Function（例：`/api/memory`）へ送る。
- 潮見は道具として記憶を引く。例：
  - `recall_corrections(title)`：似たタスクを過去にどう直されたか
  - `effort_bias()`：見積もりと実際のズレの傾向
- 似ているかの判定は、まずタイトルのキーワード一致で十分です。意味の近さで探したくなったら、Cloudflare Vectorize と Workers AI の埋め込みを後から足す候補にします。
- 潮見は Cloud Run に移るので（4）、D1 は直接読めません。`/api/memory` を通して読みます。認証は今と同じく、ユーザーの Firebase トークンを転送して確認します（新しい秘密鍵は不要）。uid ごとにデータを分けること。

### 2. 分からないときは、潮見がユーザーに聞き返す（A2A の input-required ＋ A2UI）

- タイトルがあいまいで自信が低いとき（例：「準備」）、潮見は点数をつけません。代わりに A2A のタスクを `input-required` の状態にして返します。
- 質問は A2UI のメッセージで渡します（質問文、選択肢、締切の有無など、必要な情報を聞く入力カード）。ブラウザは決められた部品だけを描きます（Transtudy と同じく、エージェントに HTML を書かせない）。
- ユーザーが答えたら、同じ taskId / contextId で潮見に送り直します。潮見は判定を再開し、答えを `clarifications` に記録します。
- 待っている間はリクエストを止めておけません。保留中のタスクは保存してください（D1 か、Cloud Run 側のタスクストア）。
- 見た目は、作る前に静止モックで基準を合わせること（ブイに「？」が付く、カードがどこに出るか、など）。

### 3. 凪が自分で潮見に相談する

- `functions/api/nagi.js` の「潮見 → 凪」の決まった順番をやめ、外側は凪を呼ぶだけにします。
- 凪に道具 `ask_shiomi(task_ids, context)` を持たせます。この道具は、潮見のエージェントカードを読み、A2A で再判定を頼みます。
- 凪への指示：判定の出どころが rule のもの、自信が低いもの、凪から見て怪しいもの（期限や残り時間と合わない、など）だけを、理由を添えて相談する。
- 1回の計画で相談できる回数に上限を設けます（時間と料金のため）。
- 潮見が聞き返した（2）ときは、凪はその質問を画面まで返して、計画を待たせます。
- trace に「誰が誰を、なぜ呼んだか」を残し、README の図とシーケンス図も新しい流れに直します。

### 4. 潮見を ADK で作り、Cloud Run で動かす

- 潮見は Python＋ADK（`google-adk` の A2A 対応）で作り直し、Cloud Run に置きます。叩き台は `docs/reference/adk-agents/`。
- 凪は Cloudflare（JavaScript）のまま。言語も置き場所も違う2つのエージェントが、A2A だけでつながる形にします。
- 潮見のエージェントカードは、2 の input-required と A2UI に対応していることが分かる内容にします。
- 認証は今と同じく、Firebase トークンを確認して ALLOWED_EMAILS で絞ります。Gemini のキーは Secret Manager に置き、リポジトリには書かないこと。
- 以前は「Vercel だけで完結（Cloud Run はやめた）」を選んでいます。Cloud Run を使う方針に変わったことを、設計書の「決めたこと」に書き足してください。
- 決めてもらうこと：使う Google Cloud プロジェクト（Transtudy と同じでよいか）、止まっている状態から起きるまでの数秒の待ちを許すか。

## 進め方の約束

- 始める前に戻す地点のタグを付ける（例：`restore/before-agents`）。
- 新しいパッケージは、作る前に GitHub で既存のものを探し、候補と採否を見せてから入れる。
- 画面に出るもの（2 のカードなど）は、静止モックで見た目を合わせてから実装する。
- コミットと公開（`npm run deploy`、Cloud Run へのデプロイ）は、ユーザーに確認してから。
- 本番で実際に動いたことを確認する。少なくとも次の3つ：凪が潮見に相談する、潮見が聞き返す → 答える → 再開する、記憶が判定に効く。
